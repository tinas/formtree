# @formtree/core

## Architecture (src)

| Folder         | Role                                                                                                                                                      |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `definitions/` | `defineField`, `defineGroup`, `arrayOf` (+ `WithDeps` variants), type-level `DraftOf` / `InputOf` / `OutputOf` / `DepsOf`, erased runtime options         |
| `state/`       | `FormState` and pure transitions (value writes, resets, array edits, errors, check states, submit flags); array items are addressed by key-based node ids |
| `validation/`  | scope walk, sync schema/validate runs, output composition, async checks, display-mode visibility                                                          |
| `nodes/`       | public node types, path navigation types, the universal runtime node object, the required probe                                                           |
| `form/`        | `createForm`, the runtime holder, operations that commit state, submit pipeline, focus                                                                    |

State is immutable; every mutation goes through a pure transition and then `commitWithValidation` / `commitState`. Side effects (timers, abort controllers, schema promises) live only in `validation/async-validation.ts` and `validation/validation-pass.ts`.

## Decisions

### Definitions and types

- Definitions carry a phantom `'~types'` and an erased `'~options'`, so definition types stay covariant (an annotated recursive definition type-checks) and runtime options are read behind one cast.
- `AnyArrayDefinition` is a non-generic interface. A generic one made `Definition` compute itself, and `createForm`'s constraint failed with TS2589.
- `activeWhen` keys are their own mapped type parameter (`ActiveKeys`). With the whole object as one parameter, the callbacks lose contextual typing and `value` is implicitly `any`.
- `defineGroup*` return `NoInfer<Children>` and `NoInfer<ActiveKeys>`. Without it, an inline nested `defineGroup({ schema })` infers `Record<string, Definition>` children from the outer call and demands `childDeps`.
- In the draft, field children are optional keys; declared groups and arrays are required and built by `createForm` (rule 7).
- An annotated recursive definition navigates its children as lens nodes and outputs the annotated type, since TypeScript cannot infer the children of a self-referencing constant. At runtime those nodes are still defined and validated.

### Values and paths

- A value is structure only when it is a plain object (prototype `Object` or `null`) or an array. Paths, array keys and `deepEqual` walk nothing else, so a `File`, a `Map`, a Temporal date or a class instance is a value of its own and compares by identity, a `Date` by its time; walking a `File` or a `Map`, which have no own keys, made any two of a kind equal. Where the definition expects a group, an object of another class becomes a plain object of its own values, so prototype getters and methods are lost and the app builds the class in its handler. A check finds a cached answer with `deepEqual`, never a string of the output, which turned every `File` into `{}` and threw on a `bigint`. `isPlainObject` and `shallowEqual` are public, and the adapters import them instead of keeping copies. happy-dom's `File` has own `name`, `type` and `lastModified` keys, so the file tests pick files that share all three. Guarded by "a field holding a file or a map is dirty once another one is chosen" and "a class instance where a group is expected keeps its values" in `create-form.test.ts`, "a group schema that returns a class instance keeps its values in the output" in `submit.test.ts`, "a check runs again for every different file, even one with the same name" and "a check accepts a bigint value" in `async-validation.test.ts`, and "lists no keys below a value that is not a plain object" in the Vue `devtools.test.ts`.
- Every read by a key from a path, a definition or a value is an own-property read (`ownValue`), so `constructor` is an ordinary key and a value on a polluted `Object.prototype` never reaches the form. A path through `__proto__` has no position (`toPath` returns `undefined`), so it reads `undefined` and ignores writes; an own `__proto__` key in the draft would set the prototype of an `Object.assign` copy of the output. Only `__proto__` is refused, since refusing `constructor` or `prototype` would forbid real field names, and values are not sanitised, so an own `__proto__` key in app data stays data. Guarded by "a path through the prototype key reaches no value and ignores writes", "a key named like an Object member is an ordinary key" and "values on a polluted Object.prototype never reach the form" in `create-form.test.ts`.
- Node ids are key-based (`cart.items.[k3].quantity`); paths shown to users use indexes. Errors, touched state and submit counts hang off the id, so a moved row needs no remapping (rule 8). The baseline keeps its own array keys, so rows rebaseline independently, and a saved new row enters it after its previous sibling.
- A write to a missing index or a removed row is ignored: no throw, state unchanged.
- Writing `undefined` to a key of a plain object removes the key, so the draft never holds an explicit `undefined`. A read still gives `undefined` (rule 7) and `deepEqual` treats a missing key and `undefined` alike, while a schema that accepts a missing key but rejects `undefined`, such as an ArkType `'key?'` or a Valibot `exactOptional`, accepts a cleared field. An array keeps its length, so `undefined` stays in a row's slot. Guarded by "a cleared optional key leaves the value valid" in `schema-libraries.test.ts`.
- `reset({ value, keepDirtyValues: true })` keeps the draft wherever `dirty` would report a change (`deepEqual` against the old initial value) and takes `value` everywhere else. It walks only plain objects found in both, so a list is kept or replaced whole: fresh rows carry no keys, and pairing them with the draft's rows by index would mix the user's rows with the server's. The new initial value's rows take the old keys at the same index, as `createForm` keys loaded rows, so an unchanged list keeps its row nodes and a row in a kept list is measured against the row at its place. Where the draft already equals `value`, it keeps its keys and the initial value takes them, so an edit saved elsewhere, an added or moved row included, becomes clean. A plain `reset({ value })` gives fresh keys, since a saved value follows the draft's row order. Without `value`, only the interactions are reset. Guarded by "changed values are kept and the new value fills everything else" and "without a value every value stays and interactions are cleared" in `create-form.test.ts`, and "a changed list is kept whole", "a row the user did not change in a kept list stays clean", "an unchanged list takes the new rows and keeps its row nodes" and "a changed list the new value already has becomes clean, its rows too" in `arrays.test.ts`.
- A schema default never fills the draft; it reaches only the output, through the schema run, so the handler and `validateAsync` receive it and a group `validate` sees `undefined`. Standard Schema cannot be asked for its defaults, and a filled draft would make "left empty" look like "chosen" and move the baseline. `guide/initial-values.md` explains it. Guarded by "a schema default fills the output, never the draft" in `submit.test.ts`.

### Validation

- Behaviour that depends on how a schema library reports issues or treats an empty value is tested against Zod, Valibot and ArkType in `schema-libraries.test.ts`, since formtree takes any Standard Schema library. Issue paths are read with `Array.from`: ArkType's path is an array subclass whose `map` builds an empty path as `[0]`, which put a field's own error on `<field>.0`. Guarded by "an error lands on the field or key it belongs to" and "a node is required when its schema rejects an empty value" in `schema-libraries.test.ts`.
- A validation pass is a scope walk, then sync runs memoised by value and deps reference, then async reconciliation. Deps are pinned by shallow equality, so a `childDeps` that returns an equal new object or array keeps the schema.
- `validate` (group, array) runs on the draft in the same step as the schema, whether or not the schema passes; neither reads the other's result. Waiting would repeat a refinement's flaw (Zod skips it while any key is `undefined` or of the wrong type), and an output exists only once the whole subtree is valid, so rules check for `undefined` and see untransformed values. Guarded by "a group validate rule runs on the draft while the schema fails" in `validation.test.ts`.
- `validateAsync` runs last, on the output, and waits while a schema or rule error targets its node or one below it, whoever produced it (`isSyncSettledAndValid` filters by `targetId`, not `ownerId`). A request costs a round trip; a sync rule costs nothing, so it never waits. Guarded by "a check waits while a parent rule puts an error on its node" in `async-validation.test.ts`.
- A check has three outcomes: no errors, errors, or no answer when `run` throws. What a check shows lives only in `FormState.checks` (`pending`, or `failed` with the thrown value); `validating` and `failedChecks` derive from it, each transition in `state/check-transitions.ts` writes it once, and `CheckEntry.status` holds only the run lifecycle. A run is current until its signal is aborted, and every path that supersedes a run aborts it, so a late answer is dropped by `signal.aborted` without a token. A failed check is not an error, since the value may be right: the input is not `aria-invalid`, `formatError` never sees it and `mode` does not hide it, but `valid` is false. Failures are not cached; a failed check runs again on its next trigger and on every `validate()` and submit, which mark it `stale`, and a run settles `idle` either way, or the settle loop would retry it within one call. A submit with errors is `'invalid'`, one whose check fails again `'unchecked'`, and both focus the node. Retries belong to the request inside `run`. Guarded by "a failed check is listed in failedChecks, not as an error", "a submit runs a failed check again and is unchecked while it still fails" and "a failure from a run that a newer value replaced is ignored" in `async-validation.test.ts`.
- `ignoreCache` (`validate`, `handleSubmit`) marks cached results `stale` before the normal pass (`settleValidationWithin`, so `form/` never touches entries). It marks the sync entries of the node, its subtree and its ancestors, since an ancestor's schema covers a schema key, and keeps them so their tokens keep rising and an earlier schema run is still rejected; settled checks in the subtree lose the cached answer a check under an asynchronous schema would read. Guarded by "ignoreCache on a schema key runs the schema and rules that cover it again" and "ignoreCache ignores the schema run it replaced" in `validation.test.ts` and "ignoreCache asks again when the schema of the checked value is asynchronous" in `async-validation.test.ts`.
- `state.required` (and `aria-required`) is true when the schema that validates a node reports an error at its path in an empty form. A field asks its own resolved schema about `undefined`; a schema key asks the nearest ancestor schema about that ancestor's structure as an empty form holds it, with the containers along the key's path written, an index segment's container being an array with a slot at that index. The answer belongs to the schema, not to the draft: one run per resolved schema and container path, memoised by definition and schema, answers every key below that path and is not asked again while the schema stays, so a change runs no schema for `required`. A question about the current draft would need a run per key on every change, which grows with the square of a group schema's keys. Requirement that changes with an answer follows `activeWhen`, since an inactive part has no schema entry, and deps, since they resolve a new schema; a key that another answer in the same schema requires, through a refinement or a union, is not marked, like one a group `validate` rule requires. Standard JSON Schema cannot answer for a field's own schema (Zod 4.6 converts `z.string()` and `z.string().optional()` alike), while validating an empty value works with any Standard Schema library. Groups and arrays are never required. A run that returns a Promise counts as not required, so `state` stays synchronous. Guarded by the tests in `required.test.ts`, "one run of a schema with the form empty answers all of its keys, and a change asks nothing again", "a key that another answer in its schema requires is not marked" and "a key of a list in the schema is asked about an empty item at its place" among them, and by "a change costs each answered key of a schema the same, however many keys it has" in `scaling.test.ts`.

### Nodes and reads

- A node is a view, not the owner of its data. Values, errors and flags live in the one immutable `FormState`, because rules cross nodes, a change commits as one step, and a schema key becomes a node object only when something asks for it.
- One runtime object per node id (`UniversalNode`); field, group and array nodes are views in types only, so `form.field('x') === form.group('x')` and adapters can key on nodes. An undeclared node reports `kind: 'lens'`, since the object cannot know which accessor returned it.
- Node interface methods are function-typed properties, so destructuring is safe and nodes stay invariant.
- A node caches its reads and keeps their reference until their content changes, because the adapters compare by identity. `state` and `attributes` are computed once per form version and keep the previous object while every member is the same reference (`shallowEqual`); `items` is cached by the array's keys; `errors`, `failedChecks` and `listErrors` (once per `listErrorsKey`) keep the previous array while their records are equal (`keepIfSame`). `value` and `initialValue` compare by reference on purpose, and records compare their members by reference, so an equal new `params` object costs a render, never a stale record. Dropping a detached node drops its caches. Guarded by "node state keeps its reference while nothing about the node changes", "node state with visible errors keeps its reference while another node changes", "attributes keep their reference while no attribute changes", "an error list keeps its reference while the listed errors stay the same" and "error lists are kept per meaning of their options" in `create-form.test.ts`, and "the item list keeps its reference until the keys change" in `arrays.test.ts`.
- Node state finds errors and paths through indexes derived by reference instead of scans: the active errors by target together with every target's ancestors, rebuilt when `errors` or `inactive` changes, and each path set's paths with their ancestors. Every read node used to scan every error and touched path, so a keystroke grew with the square of the form. Guarded by "a change costs each field that reads the form the same, however large the form" in `scaling.test.ts`, which compares two sizes in one run so the machine's speed cancels out.
- Every node carries an internal `subscribeToForm` (every change) and `version` (the commit count), so an adapter that holds only a node can follow anything a reader may read, as React's `useNodeState` does.
- A node's `subscribe` runs only when its `state` or path changes; the form's runs after every change, because a summary or a save reads across nodes. A group's `state` does not follow everything below it, so a part shows its fields through their own subscriptions. Guarded by "a node subscriber is notified only when that node changes, once per batch" in `create-form.test.ts` and "a field subscriber is notified when its row moves" in `arrays.test.ts`.
- `setDeps` with dependencies equal key by key does nothing. React passes a new `deps` object on every render, and a notification would loop.

### Submitting, focus and errors

- `handleSubmit` handlers receive only the output; the caller already holds the node.
- The function `handleSubmit` returns takes no event and never calls `preventDefault()`. The code that binds the event prevents the default, so no behaviour is hidden.
- `shouldFocusError` picks the focus target (the first element shown on the page with an error or a failed check, in document order, or the summary) and `focusElement` (default `element.focus()`) acts on it. Focus moves once every check has settled and `onInvalid` (awaited) has run, so the DOM knows the order and what is hidden (`checkVisibility`), and the component that owns a closed dialog opens it in `onInvalid`. `handleSubmit` overrides both, `node.focus()` uses the form's, and sticky headers use CSS `scroll-margin-top`. Guarded by "the first invalid field on the page receives focus", "focus skips an error whose element is hidden, such as one in a closed dialog", "onInvalid can open the dialog a field is in before focus moves", "focus waits for onInvalid, so a field it renders can receive focus" and "focus moves once every check has answered, so a slow check above a sync error gets it" in `submit.test.ts`.
- Errors are listed in definition order: by the node that produced them (a node before the nodes declared below it, `children` in declared order, rows in list order), a field's errors together where its first one falls, and within one node schema, `validate` and checks before external errors, each in the order it returned them. A schema's errors keep its own order, the only key order a Standard Schema reveals. Path order put `email` before `name`, and DOM order would make a cached read depend on rendering. `listErrors`, `state.errors` and `onInvalid` share the order. Guarded by the tests in `error-order.test.ts`.
- `FormError.code` is the message the schema reports, a readable text or a translation key; the library's own issue code lands in `params.code`.
- Errors become text only through `formatError` (default `error => error.code`), which feeds `errorMessage` and `form.formatError`. `errorMessage` is a getter outside the memoised `state`, so a formatter that reads the current language runs again where the message is read.
- `FormDefaults` are the options an app sets once, and the adapters take them app-wide. An option given to `useForm` wins, and an explicit `undefined` falls back to the default, as `??` does.

### Events

- `form/form-events.ts` emits `@internal` `FormEvent`s for devtools through `UniversalNode.observe`. Operations emit after they commit; a cached check result and an aborted check are emitted during the pass, before the commit. A `'skipped'` submit and a check result emit without a state change, which is why events are separate from `subscribe`. With no observer an emit is one size check, and behaviour never depends on events.
